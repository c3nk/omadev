# Omadev v0.1.0 — Validation Report

> Status: v0.1.0 functionally complete. Summary of what was built, how it was tested, and what
> was deliberately deferred.

## Implemented

- **`omadev inspect`** — read-only detection of the stack (Docker Compose, Dockerfile, Node.js and
  its package manager, React/TypeScript/Vite/Vitest, Python and its dependency manager,
  FastAPI/pytest, PostgreSQL, mise runtimes), with HIGH/MEDIUM/LOW confidence.
- **`omadev up`** — safe lifecycle: detect → check → plan → show → confirm → execute → verify.
  Runs only at HIGH confidence on a Compose project; shows the exact command; verifies service
  state after starting.
- **`omadev down`** — stops the environment and never removes volumes.
- **`omadev status`** — per-service state (`running`/`healthy`/`unhealthy`/`stopped`/`unknown`)
  and published ports.
- **`omadev logs`** — streams `docker compose logs -f`.
- **bare `omadev`** — informational overview; never offers to start (D1).
- Docker privilege detection at runtime (no hardcoded `sudo`, D4); Compose v2 only (A2);
  environment reporting that never reads secret values.

## Tests

- 58 unit tests across all packages (`go test ./...` green), plus detector fixtures under
  `testdata/`.
- Executor and command logic are tested with a fake executor — no Docker daemon required.
- A build-tagged integration test (`-tags=integration`) runs the real `docker compose` in a
  separate Linux CI job.
- **Live validation:** the real up → status → down cycle was run against Docker on an image-only
  fixture; it started a container, reported it running, stopped it, and left nothing behind.

## Known limitations

- Compose parsing covers common layouts; profiles, arbitrary `-f` chains, and extra override files
  are reported as ambiguous rather than supported.
- Ports using `${VAR}` interpolation are not resolved (by design) and so are not shown.
- `status` parsing relies on `docker compose ps --format json` (Compose v2).
- Python detection scans file contents (no TOML parser dependency), so unusual dependency
  declarations may be missed.
- Project-root discovery is upward-only; a Compose file in a child directory is not auto-found.
- `omadev inspect` displays commands without the runtime `sudo` probe that the execution commands
  apply; the shown command may omit `sudo` where elevation is actually required.
- No `.omdev.yaml` support (deferred).

## Security considerations

- Repository contents are treated as untrusted input; no repository-defined script is executed
  during inspection.
- All subprocess calls are structured argv — no shell interpolation.
- Detection is confined to the project root by `os.Root`, refusing symlink escapes.
- Secret values are never read or printed; `.env` reporting lists variable names only.
- Docker privilege is detected, never modified; groups and security settings are never changed.
- Release binaries are checksummed; the AUR package pins those checksums at publish time.

## Deferred features

- Native (Docker-less) execution via Node/Python/Go/Rust/mise (M3).
- `omadev test` / `shell` / `open` / `exec`, port-conflict detection, richer health checks (M4).
- `omadev new` project scaffolding (M5).
- Omarchy-native integration: notifications, Hyprland/Quickshell, launchers (M6).
- `.omdev.yaml` configuration.

## Recommended next steps

1. Push to GitHub so CI (unit + integration) runs, and tag `v0.1.0` to trigger the release
   workflow (binaries + checksums).
2. Publish the AUR packages, filling in the real checksums from the release.
3. Begin M3 (native execution) behind the existing model → plan → executor pipeline.
